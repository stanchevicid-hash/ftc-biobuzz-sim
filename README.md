# FTC BIOBUZZ Simulator (сезон 2026–27)

Веб-симулятор FIRST Tech Challenge: пишете обычный FTC-код на Java (LinearOpMode / OpMode) — он **компилируется без изменений**
против подменного FTC SDK 12.0 и управляет виртуальным роботом на 3D-поле BIOBUZZ с физикой. Робот делает только то, что написано в коде.

## Запуск

```
start.bat            (Windows; первый запуск сам соберёт SDK и мост)
./start.sh           (macOS / Linux)
start.bat --rebuild  (пересобрать после правок в sdk/ или server/)
```

Откроется `http://localhost:8740`. Нужна **Java 8+** (подходит JRE; в Android Studio есть своя — `…\Android Studio\jbr\bin`).
Интернет не нужен: three.js, Rapier, OpenCascade и компилятор лежат в проекте.
Сервер слушает только 127.0.0.1: порт 8740 (страница и API) и 8741 (WebSocket для шага симуляции — ~0.1 мс вместо 1–6 мс у HTTP,
поэтому прогоны идут до ~7× быстрее реального времени). API принимает запросы только со страниц самого симулятора (проверка Origin/Host):
иначе любой открытый сайт мог бы отправить Java-код на компиляцию и запуск.

**Замеры для калибровки**: OpMode `MeasureRobot.java` (Code → Add examples) запускается на настоящем роботе и выдаёт ровно те числа,
что просит вкладка Calibration (скорость вперёд по энкодерам, страйф по двум замерам рулеткой 1 с и 2 с, время оборота по IMU, тест энкодера).

### Удобства
* **Своя стартовая позиция**: «Старт → Своя позиция…» — числами (дюймы, курс) или «📍 указать на поле»: 1-й клик — место, 2-й — куда смотрит робот.
* **График телеметрии**: любые `telemetry.addData("имя", число)` рисуются за последние 15 с — удобно настраивать PID.
* **Подсветка Java** в редакторе, Ctrl+S — собрать.
* **IMU как на роботе**: на вкладке «Робот» указывается, как реально стоит Control Hub (логотип/USB). Показания считаются через объявленную в коде `RevHubOrientationOnRobot` — та же математика, что в SDK.
* **Техосмотр робота** (вкладка Robot → Inspection, запускается после каждой смены робота): R102 старт 18″, R105 18×24×29″ во всех положениях шарниров,
  R503 8+8, R502 мощность серво, ЦТ и запас до опрокидывания, X-раскладка роликов mecanum, хватит ли мотора/серво поднять механизм, дубли имён;
  затем тест-заезды в симуляторе: скорость вперёд/вбок, разворот, ход каждого шарнира, проседание без питания (`web/js/inspect.js`).
* **Свои имена устройств**: если в коде команды мотор называется `leftFront`, а у робота `frontLeft`, после сборки под кнопками Init/Start
  появится список несовпадений с угаданной парой — «Use these names» сохраняет соответствие в конфиге робота (`aliases`), код не меняется.
* **Разделы**: Match (матч и Driver Station), Test bench (шутер, интейк, шасси, лифт/рука по отдельности + Auto ×N), Robot (загрузка, техосмотр, калибровка), Code, Settings (графика, звук, геймпады, шумы датчиков), Help.
* **Test bench** (`web/js/bench.js`): шутер стреляет в CELL с заданной дистанции — RPM до/после выстрела, восстановление, скорость вылета, высота, попал/нет; Sweep строит таблицу дистанция × худ; интейк — время на каждый мяч; шасси — скорость, разгон, тормозной путь; лифт — время хода, держит ли без питания, ток.
* **Звуки поля** (таблица 9-1): старт, конец автонома, «Drivers, pick up your controllers», колокола, 1:00, 0:20, финал.
* **Клавиатура**: кнопка **Keys** под полем. W/S вперёд-назад, A/D вбок, ←/→ разворот, Shift — медленно (40% стика).
* **AprilTag robotPose**: считается формулой SDK 12 с учётом `setCameraPose` (для тегов/кластеров с позицией на поле).
* **Второй робот**: «Driver Station → Второй робот» — партнёр по альянсу или соперник (демо-робот), едет от **gamepad2**. Роботы сталкиваются,
  соперник может толкать: заторможенный робот держит ~20 Н, сильнее — колёса проворачиваются, как у настоящего (защита в игре).
* **След робота** (〰) — путь по полю за текущий прогон.
* **⤓ CSV** — лог прогона 50 Гц: поза (дюймы/°), каждый мотор (мощность, скорость, энкодер, ток), батарея и все числа из telemetry.
  Подходит и для анализа PID в Excel/Sheets, и для вкладки «Калибровка» (лог мотора).
* **⏮ Повтор** — перемотка последнего прогона ползунком (×0.5/×1/×2) с телеметрией того момента; «выйти» — поле сбрасывается.

## Проверки (регрессия)

## Архитектура и почему так

```
браузер (web/)                                   локальный Java-мост (server/ + sdk/)
 ├ Rapier 3D (WASM): поле, робот, мячи, 400 Гц     ├ ECJ (Eclipse compiler) компилирует ваши .java
 ├ «прошивка хаба»: PID скорости/позиции          ├ подменный FTC SDK 12.0 (те же пакеты и сигнатуры)
 ├ датчики, AprilTag, счёт, three.js-рендер       └ ваш OpMode в отдельном потоке
 └ каждые 10 мс: POST /api/sync {датчики, геймпады} ⇄ {команды моторов/серв, telemetry}
```

**Запуск Java — локальный мост на JVM**, а не CheerpJ/TeaVM:
* код идёт на **настоящей JVM** — те же потоки, исключения, `String.format`, коллекции, что и на роботе; стек-трейсы с номерами строк;
* компилятор ECJ — один jar, работает на голой JRE 8 (javac/JDK не нужен), понимает Java 8 — тот же уровень, что OnBot Java/Android;
* CheerpJ (JVM в браузере) медленно стартует javac, требует лицензию для коммерческого использования и сложен в связке «нативные вызовы ↔ физика»; TeaVM всё равно требует серверной компиляции и не поддерживает многопоточный LinearOpMode;
* **lockstep**: OpMode доходит до «точки цикла» (`opModeIsActive()`, `sleep()`, `idle()`, конец `loop()`), и только потом физика делает следующий шаг 10 мс. Поэтому прогоны повторяемы, симуляцию можно ставить на паузу и ускорять (×4, а «Разброс» — так быстро, как отвечает JVM). `ElapsedTime`, `sleep()`, `getRuntime()` идут по времени симуляции.

Физика робота: шасси — твёрдое тело на «лучевой» подвеске; колесо толкает только вдоль направления, перпендикулярного оси роликов
(mecanum ±45°, omni — вдоль качения, traction — с боковым сцеплением), импульс ограничен μ·N → проскальзывание при резком старте и столкновениях.
Мотор — DC-модель `T = T_stall·(V/12 − ω/ω_free)`, редуктор, отражённая инерция ротора, сухое и вязкое трение, батарея с внутренним сопротивлением.

## Допущения (не опубликованы — оценены, все настраиваются)

* Момент, удерживающий HIVE: 0.45 Н·м — 3 стартовых NECTAR держат, ещё ~2–4 POLLEN опрокидывают (`web/js/field.js`, `HIVE.tipTorque`).
* Массы мячей: POLLEN 28 г, NECTAR 55 г; трение мяч/плитка 0.5, отскок 0.45.
* Боковое «скрабирование» mecanum 0.12 (страйф ≈ 90% от скорости вперёд); подгоняется на вкладке «Калибровка» по замеру реального страйфа.
* Положения FLOWER, LOADING ZONE, GARDEN сняты с рисунков манула (точность ±1″, как и сам допуск поля); геометрия рамы HIVE упрощена (4 ноги + перекладина).
* Захват/выброс мячей — «зона захвата + слоты + скорость вылета от маховика», а не контакт резины с мячом.
* Ориентация хаба: если хаб стоит боком, а в коде объявлен «логотип вверх», ошибка проявляется в pitch/roll и в нестабильном yaw (как в SDK); тонкие эффекты калибровки самого чипа IMU не моделируются.

## Свой робот: советы

* Onshape: правый клик по вкладке сборки → **Export** → STEP (или GLTF). Большие STEP (100+ МБ) разбираются до нескольких минут — это в фоне, страница не зависает.
* Роли деталей определяются по названиям и артикулам (`5203-2402-0019` → мотор 312 RPM, `3213-3606…` → mecanum, `REV-31-1557` → датчик цвета и т. д.) — проверьте таблицу.
* Имена устройств в таблицах = имена в `hardwareMap.get(...)` вашего кода.
* «Экспорт .json» сохраняет конфигурацию **вместе с 3D-моделью** — один файл можно отправить команде.
* Библиотеки (Road Runner, Pedro, FTCLib…): положите `.java` или `.jar` в `libs/`.

## Ограничения — честно

* Захват и выброс мелких игровых элементов симулируются **приближённо**.
* Поломки, люфты, провода, нагрев моторов, деформация мячей **не симулируются**.
* Камера определяет AprilTag геометрически (поле зрения, размер, перекрытие, шум) — собственные `VisionProcessor`/OpenCV-конвейеры не получают кадр.
* Не поддержаны: OctoQuad, SparkFun OTOS, HuskyLens, navX, MR-датчики, старый `BNO055IMU`, Blinkin, `ColorBlobLocatorProcessor`/`PredominantColorProcessor`.
* **Перед соревнованием всё равно нужна проверка на реальном поле.**
